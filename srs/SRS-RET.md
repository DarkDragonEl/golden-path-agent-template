### 0.1 Tailoring declaration

Per the working standard: sections of ISO 29148 §9.5 with no content for a blueprint demo component are marked *Not applicable — tailored out* with a one-line reason, never silently omitted. This document keeps the full seven-section skeleton of `srs/SRS-APR.md` and `srs/SRS-AGT.md` — unlike `srs/SRS-MIT.md`'s interface-only depth, which structurally omits §§1/3/5–7 by mission directive. That structural omission does not apply here: this document's assigned depth is **Medium** (`MISSION_PHASE_B0.md`'s deliverable table: "Retrieval + ingestion service | Medium | SysR-P-IF-04, SysR-P-F-10"), not interface-only. Medium depth is expressed as: every section present and real, but populated more lightly than the Full-depth siblings — 11 requirements total in this document, against `srs/SRS-APR.md`'s 18 and `srs/SRS-AGT.md`'s 25. §5 (Quality) is tailored out with a one-line reason below, using the same mechanism `srs/SRS-APR.md` uses for its own Performance tailoring — a documented, reasoned omission, not a structural one. Verification methods: I (inspection), A (analysis), D (demonstration), T (test) — same conventions as the SyRS and its sibling SRS documents. Where two methods are listed, the first is primary.

### 0.2 Purpose and scope of the software item

The retrieval and ingestion service curates the platform's approved knowledge corpus and serves it to retrieval clients. It realizes two obligations stated together in SysR-P-F-10: attaching governance metadata — owner, classification, version or effective date, access policy, and source — to every corpus document at ingestion, and supporting a documented refresh process under which an updated document version supersedes the prior one for subsequent citation. It also realizes SysR-P-IF-04's retrieval contract: accepting a query and the initiating user's identity, and returning passages carrying source-document identity and governance metadata, filtered to what that user is authorized to view, before any passage reaches the calling client. In this blueprint the sole retrieval client is the pilot agent (`srs/SRS-AGT.md`, SRS-AGT-IF-03); the contract below is stated generally enough — in terms of "the calling client," not "the agent" — that a second adopting team's agent, built for a different knowledge domain (SyRS §0.1), can consume it unchanged.

Out of scope for this item: the agent's use of retrieved passages, answer composition, and citation assembly (`SRS-AGT`, specifically SRS-AGT-F-01); the ranking/matching algorithm's internals and the vector-store/search-index technology selected to realize retrieval (a realization choice, SysR-P-LC-02 — no product is named in this document); the mock enterprise tool and its MCP contract (`SRS-MIT`); evaluation scoring of retrieval relevance and citation quality as an evaluated dimension of agent behavior (`SRS-EVH`, not yet derived, and `srs/SRS-AGT.md`'s SRS-AGT-QUAL-01, which already claims SysR-A-EVL-01 for the pilot agent) — this document is the retrieval-relevance signal's *provider*, not its evaluator, and does not duplicate that ownership.

## 1. Functional Requirements (SRS-RET-F-*)

- **SRS-RET-F-01 — Ingestion metadata attachment.** Before any corpus document becomes retrievable through SRS-RET-IF-01, the ingestion process shall attach to it: an owner, a classification, a version or effective date, an access policy, and source metadata. A document for which any of these attributes has not been attached shall not become retrievable. This "before retrievable" gating is not an arbitrary addition: it is the direct consequence of combining this clause of SysR-P-F-10 with SysR-P-IF-04's own promise that every returned passage carries source-document identity and owner/classification metadata — a document with incomplete governance metadata could not honor that promise if served. It is not marked PROPOSED for that reason, the same forced-by-extension posture `srs/SRS-AGT.md` uses at SRS-AGT-F-08.
  *Trace:* SysR-P-F-10. *Verification:* D (OS-06), I (metadata schema, per SRS-RET-DATA-01). Evidence: `eval/corpus-manifest.yaml`'s 20 exemplar documents, each carrying all nine fields (`doc_id`, `title`, `owner_role`, `classification`, `version`, `effective_date`, `access_policy`, `source`, `refresh_process`) — confirmed by direct inspection during this derivation, not assumed from memory.

- **SRS-RET-F-02 — Documented refresh process.** The platform shall support a documented process by which a corpus document is refreshed to a new version or effective date; from the moment a refresh completes, SRS-RET-IF-01 shall serve the refreshed version as the current one, and subsequent agent answers grounded in that document shall cite the updated version. The retrieval interface shall never return a superseded version as current. This is not marked PROPOSED: it restates SysR-P-F-10's second clause directly ("shall support a documented refresh process such that an updated document version is cited by subsequent answers"), the same forced-by-extension posture `srs/SRS-AGT.md`'s SRS-AGT-F-08 uses for a requirement forced by extension of already-confirmed text.
  *Trace:* SysR-P-F-10. *Verification:* D (OS-06), I. Evidence: `eval/corpus-manifest.yaml`'s `refresh_process` field, populated for all 20 documents (e.g., PLAT-001: "Reviewed quarterly by Platform Engineering; superseded versions archived, not deleted") — establishes the process exists as a documented per-document commitment at Phase A. No Phase A eval case exercises an actual refresh-then-recite sequence (a document version changing between two evaluation runs), since `eval/cases/domain/*.yaml` are static, single-version fixtures — noted honestly as a Phase B integration-test need, not evidence available yet.

- **SRS-RET-F-03 — Authorization-filtered results.** Every result set returned through SRS-RET-IF-01 shall be filtered against the initiating user's authorization, evaluated per candidate document against that document's `access_policy` attribute (SRS-RET-F-01, SRS-RET-DATA-01), before any passage is returned to the calling client. A document the initiating user is not authorized to view shall never appear in the result set — not as a full passage, not redacted, not merely named.
  *Trace:* SysR-P-IF-04, SysR-P-SEC-02. *Verification:* T (authorization-filtered retrieval cases). **Coverage gap, noted honestly and consistently with `srs/SRS-AGT.md`'s SRS-AGT-F-02:** no file in `eval/cases/domain/` currently exercises the authorization-*negative* dimension of this requirement (a query for a document the initiating user is not authorized to view). This is the same Phase A eval-set gap already recorded at SRS-AGT-F-02/SRS-AGT-IF-03; it is restated here, not raised as a new gap, because it is one gap visible from two sides of the same contract (agent-consumer side at SRS-AGT-F-02, retrieval-provider side here). Both requirements need the same future eval-set addition (recommended: a dedicated corpus-authorization case in `eval/cases/domain/itsm_read.yaml` or a new adjacent file) to close.

- **SRS-RET-F-04 — Synthetic-only corpus content.** Every corpus document distributed with this blueprint, and every document used to exercise SRS-RET-IF-01/SRS-RET-IF-02 in local development or CI environments, shall be synthetic or public sample data; no corpus document shall contain organization-identifiable content. This is not marked PROPOSED: it restates SysR-P-INFO-04's "seeded corpora" clause directly, and discharges the deferral `srs/SRS-AGT.md`'s own scope note already makes ("Synthetic-only demo content (SysR-P-INFO-04) is enforced by the corpus (SRS-RET) ... owners for their own content") — this requirement is that discharge.
  *Trace:* SysR-P-INFO-04. *Verification:* I (content review). Evidence: `eval/corpus-manifest.yaml`'s header comment ("All documents, roles, and figures below are synthetic") and its 20 entries (invented role titles, invented document titles, no real hostnames/URLs/figures — confirmed by direct inspection); `corpus/README.md`'s existing scaffold commitment is consistent with, though not itself the authoritative field set for, this same posture.

## 2. Interfaces (SRS-RET-IF-*)

- **SRS-RET-IF-01 — Retrieval query interface (offers SRS-AGT-IF-03's contract).** The service shall expose a retrieval operation accepting, at minimum, a free-text `query` and the initiating user's identity, and optionally a result-count limit (`top_k` — the field name follows the existing scaffold at `agent/retrieval_client.py`'s stub signature). `PROPOSED — pending owner review:` where `top_k` is omitted, the service shall apply a default sourced from deployment configuration, not a value fixed in this document or hardcoded in the service. Rationale: this follows the configuration-injection posture `CLAUDE.md` states generally ("environment differences live only in config, secrets, policy bundles, and bindings") and the pattern SysR-P-IF-08 establishes for other environment-specific values elsewhere in this SyRS; SysR-P-IF-08's own enumerated config-schema fields do not explicitly list a retrieval result-count default, so this is an extension by analogy, not a value forced by direct SyRS text — hence the marker, unlike SRS-RET-F-01/F-02/F-04/SEC-02 elsewhere in this document, which are forced by extension and say so explicitly instead of carrying this marker. Alternative considered: a fixed default hardcoded in the service, matching the existing `agent/retrieval_client.py` scaffold's `top_k: int = 5` — simpler, requires no config-schema addition, but inconsistent with the configuration-injection posture applied to every other environment-specific value in this document and its siblings; not adopted here, but not ruled out by SyRS text alone either. (This PROPOSED default-sourcing rule diverges from `retrieval_client.py`'s current hardcoded `top_k: int = 5` default, which is itself a pre-existing scaffold placeholder explicitly marked `TODO(domain)`, not a normative claim of this document.) The service shall return, for each matching passage, at minimum: `passage_text`, `doc_id` (source document identifier), `title`, `version`, `effective_date`, `owner_role`, `classification`, and `source` — with SRS-RET-F-03's authorization filter already applied to the returned set before any passage reaches the calling client. (This field-name set also diverges from `retrieval_client.py`'s current `RetrievedChunk` dataclass — `doc_id`, `title`, `snippet`, `source_uri`, `classification`, `version` — which uses `snippet` and `source_uri` where this document uses `passage_text` and `source`, and has no field at all for `owner_role` or `effective_date`. Like the `top_k` default above, `RetrievedChunk`'s field names are a pre-existing `TODO(domain)` scaffold placeholder, not a normative claim of this document, and are superseded by the naming specified here — flagged as a Phase B update target for that module, not a divergence this document needs to reconcile itself.)

  This interface satisfies, field for field, the retrieval-client contract `srs/SRS-AGT.md`'s SRS-AGT-IF-03 states as authoritative pending this document (`DECISIONS.md` DEC-001): SRS-AGT-IF-03 requires, at minimum, a query and initiating-user-identity input, and passage output carrying passage text, source document identifier, document version or effective date, and owner/classification metadata — every one of those fields is present above. This interface **widens** SRS-AGT-IF-03's minimum ask rather than narrowing it: where SRS-AGT-IF-03 asks for "document version or effective date" (either), this interface returns both `version` and `effective_date`; where SRS-AGT-IF-03 asks for "owner/classification metadata" in the abstract, this interface commits to the concrete field names `eval/corpus-manifest.yaml` already establishes at Phase A (`owner_role`, `classification`), plus two additional fields SRS-AGT-IF-03 does not require at all (`title`, `source`). No field SRS-AGT-IF-03 asks for is omitted, redefined, or returned under a different name than a reasonable reading of "at minimum" would accept. `srs/SRS-AGT.md`, when next revised, may cite these concrete field names directly instead of its own abstract phrasing, at the owner's discretion; this document does not require that revision.
  *Trace:* SysR-P-IF-04; SysR-A-F-01, SysR-A-F-02 (referenced — the agent-side obligations SRS-AGT-IF-03 already claims against these two SysRs; SRS-RET-IF-01 is the provider-side contract those obligations depend on). *Verification:* T (authorization-filtered retrieval cases; field-for-field conformance check against SRS-AGT-IF-03). Evidence: `eval/cases/domain/knowledge_qa.yaml` (KQA-001..015) exercises the passage/source-identifier half of this contract at the agent-observable level (`source_doc_ids` values — e.g., KQA-001 → `["PLAT-003"]`, KQA-008 → `["PROC-001", "PLAT-002"]` — confirmed to resolve against real `doc_id` entries in `eval/corpus-manifest.yaml`); the authorization-filtering half has no Phase A negative-case evidence, per the gap noted at SRS-RET-F-03.

- **SRS-RET-IF-02 — Document metadata/manifest interface (demo/test-support only).** The service shall additionally expose a query-by-`doc_id` operation returning one document's complete metadata record (the fields of SRS-RET-DATA-01) without requiring a free-text match — for demo and test corpus-state verification, and for the future evaluation harness's (`SRS-EVH`, not yet derived) citation-validity checks, which must resolve `eval/cases/domain/knowledge_qa.yaml`'s `expected.source_doc_ids` values against actual corpus identity (the same role `eval/validate.py` already performs by reading `eval/corpus-manifest.yaml` directly at Phase A, per `eval/README.md`). This mirrors `srs/SRS-MIT.md`'s SRS-MIT-IF-04 "exists alongside, not instead of" pattern: it is never called by the agent as part of the retrieval-client contract — SRS-AGT-IF-03 names only the query operation of SRS-RET-IF-01 — and it is not a second retrieval path.
  *Trace:* SysR-P-IF-04 (informative — this surface exists alongside, not instead of, the retrieval contract proper; the agent never uses it). *Verification:* I (schema inspection), T (state visible via this interface matches state returned via SRS-RET-IF-01 for the same document). No Phase A eval case exercises this interface directly; `eval/validate.py`'s existing structural checks against `eval/corpus-manifest.yaml` are the closest Phase A analogue, performed today by reading the manifest file directly rather than through a service interface — this document specifies the future service-level equivalent.

- **SRS-RET-IF-03 — Retrieval-event telemetry.** For every retrieval invocation (SRS-RET-IF-01), the service shall emit, via the platform telemetry interface, a retrieval-event span or event carrying at minimum: the query received, the set of passages returned (by `doc_id` and `version`), and the authorization-filter outcome (how many candidate documents were filtered out for the initiating user, if any) — correlated to the originating request and session identifiers. This is a light, single-item interface claim, deliberately scoped to match `srs/SRS-APR.md`'s own single-item telemetry claim (SRS-APR-IF-03) for the events that document itself emits, consistent with this document's Medium-depth restraint: it is not a restatement of the agent's own aggregate telemetry obligation (SRS-AGT-IF-08, which re-surfaces what each provider, including this one, already emits), but the provider-side emission SRS-AGT-IF-08 depends on existing at all.
  *Trace:* SysR-P-IF-06 ("retrieval event" is one of the five OTLP span/event categories SysR-P-IF-06 names explicitly). *Verification:* T (trace-completeness assertions; Phase D dashboard, matching `srs/SRS-APR.md`'s SRS-APR-IF-03 verification pattern exactly). No Phase A eval case — telemetry emission is not black-box observable through `eval/cases/domain/`; a Phase B/D trace-continuity check is needed, the same evidence posture SRS-APR-IF-03 and SRS-AGT-IF-08 both carry.

Note: this document does not add a formal ingestion-API interface item. "Ingestion process" in SysR-P-F-10 is a behavioral guarantee, discharged above as SRS-RET-F-01/SRS-RET-F-02; the SyRS text gives no textual support for a specified, agent-facing or operator-facing ingestion protocol surface, and inventing one here would be scope creep for a Medium-depth document (CLAUDE.md's scope-guard discipline applies to documentation, not only to code).

## 3. Data Requirements (SRS-RET-DATA-*)

- **SRS-RET-DATA-01 — Document metadata schema.** Each corpus document's metadata record shall persist exactly the field set `eval/corpus-manifest.yaml` already establishes at Phase A: `doc_id`, `title`, `owner_role`, `classification`, `version`, `effective_date`, `access_policy`, `source`, `refresh_process`. This document formalizes that Phase A contract **without revision** — carried forward unchanged, the same posture `srs/SRS-MIT.md` used for `eval/README.md`'s ITSM tool contract. This is the first live check of the corpus-manifest analogue of `srs/SRS-MIT.md`'s same-PR sync rule (any future change to this nine-field set must land in the same PR as a revision to `eval/corpus-manifest.yaml` and to this requirement); like `srs/SRS-MIT.md`'s own first check of its rule, this check **found nothing to do** — all nine fields were confirmed present, by direct inspection, on all 20 exemplar documents during this derivation.
  *Trace:* SysR-P-F-10. *Verification:* I (schema inspection against `eval/corpus-manifest.yaml`). Evidence: `eval/corpus-manifest.yaml`, all 20 entries.

- **SRS-RET-DATA-02 — Superseded-version retrievability.** `PROPOSED — pending owner review:` a superseded document version shall remain retrievable through SRS-RET-IF-02 (metadata interface), by explicit version, after SRS-RET-F-02's refresh process makes a newer version current through SRS-RET-IF-01; a superseded version shall not be served as current, but it shall not be deleted or made permanently unretrievable either. Rationale: this is consistent with, though not directly forced by, `eval/corpus-manifest.yaml`'s own exemplar `refresh_process` text — PLAT-001's entry states "superseded versions archived, not deleted," a pattern this requirement generalizes into a normative retrieval-side guarantee. It is cited here **by analogy, not direct trace**, to the platform's retention posture for approval/audit records (SysR-P-SEC-06, SysR-P-INFO-03): those requirements are about approval and audit records specifically, not corpus document versions, and this document does not claim they extend to corpus content directly — the analogy is only that the platform's general posture elsewhere favors archival over deletion, which makes this reading the more consistent one, not the only textually forced one. Alternative considered: pure current-only retrieval — hard-delete or hide a document version entirely once superseded — rejected as weaker audit/citation-history support (an agent answer, or an approval proposal's `evidence_refs`, that cited a now-superseded version would become unverifiable after refresh) and inconsistent with the archival posture `eval/corpus-manifest.yaml` itself anticipates for at least one exemplar document.
  *Trace:* SysR-P-F-10 (by extension — the refresh-process clause implies *some* disposition for a superseded version; this document proposes retention over deletion). This gap is recorded as `srs/FINDINGS.md` **FIND-005**. *Verification:* T (a superseded version remains queryable by explicit version through SRS-RET-IF-02 after a refresh, and is absent from SRS-RET-IF-01's current-result set). No Phase A eval case — corpus version history is not exercised by any case in `eval/cases/domain/`, which are single-version, static fixtures; a Phase B integration test is needed once ingestion/refresh (SRS-RET-F-01/SRS-RET-F-02) is implemented.

## 4. Security Requirements (SRS-RET-SEC-*)

- **SRS-RET-SEC-01 — No shared credentials on the corpus access path.** The service shall be accessed, and shall itself access any underlying document store, only under authorization derived from the initiating user's identity and/or the calling workload's identity; no broadly shared credential shall be used on any leg of the corpus access path. This is the provider-side complement of `srs/SRS-AGT.md`'s SRS-AGT-SEC-01, which already claims the consumer (agent) side of this same guarantee for the corpus access path specifically; it mirrors the provider/consumer split `srs/SRS-MIT.md`'s SRS-MIT-SEC-01 and `srs/SRS-AGT.md`'s SRS-AGT-SEC-02 already established for the SysR-P-SEC-03/SysR-P-POL-01 pair at the tool boundary — here, for SysR-P-SEC-02, at the retrieval boundary.
  *Trace:* SysR-P-SEC-02 (provider side; SysR-P-SEC-02's own text — "broadly shared credentials shall not be used on any access path" — is general enough to reach the service's own access to its backing store, not only the agent's access to the service). *Verification:* I (credential inventory), T (access under distinct identities asserted in audit records). No Phase A eval case — credential provisioning is not black-box observable through `eval/cases/domain/`; a Phase B identity-inspection test is needed, the same evidence posture `srs/SRS-AGT.md`'s SRS-AGT-SEC-01 carries.

- **SRS-RET-SEC-02 — No client-facing write path.** SRS-RET-IF-01 and SRS-RET-IF-02 shall expose no operation that creates, modifies, or deletes corpus content or corpus metadata; ingestion (SRS-RET-F-01) and refresh (SRS-RET-F-02) shall be reachable exclusively through the platform's ingestion process, never through either client-facing interface. No client, including the pilot agent (`srs/SRS-AGT.md`'s SRS-AGT-IF-03), shall be able to write to the corpus through this service. This is not marked PROPOSED: SRS-RET-IF-01's own definition is a query-in/passages-out contract that names no write verb at all, and SRS-RET-F-01/SRS-RET-F-02 already structurally separate ingestion (a platform-internal process) from retrieval (the client-facing read interface) — the guarantee follows directly by extension of requirements already stated in this document, the same forced posture `srs/SRS-AGT.md`'s SRS-AGT-F-08 and `srs/SRS-MIT.md`'s SRS-MIT-SEC-01 both use.

  Two SysR requirements were considered as candidate anchors and deliberately **not** cited, despite each naming a "disallowed write"/"read-only" concept: SysR-P-SEC-03 is textually scoped to "Tool-side credentials" and SysR-P-F-09 (an MCP/tool-contract concept), already fully discharged by `srs/SRS-MIT.md`'s SRS-MIT-SEC-01 for the tool boundary — no textual hook connects it to corpus or retrieval credentials, and citing it here would duplicate an already-owned obligation under a mis-scoped anchor. SysR-P-SEC-05 names only "an unauthorized tool call or a disallowed write" as its two deny-path instances, both tool/write-path concepts already discharged by `srs/SRS-APR.md`'s SRS-APR-SEC-01 and `srs/SRS-AGT.md`'s SRS-AGT-F-06; its own StR lineage (StR-SEC-04) is disjoint from SysR-P-IF-04's (StR-USR-01, StR-SEC-02, StR-SEC-03), and the SyRS's own author never links the two. This requirement is grounded directly in SysR-P-IF-04's and SysR-P-F-10's own text instead, which is the more textually honest anchor and avoids an invented, unforced trace.
  *Trace:* SysR-P-IF-04 (by extension — the retrieval contract defined there names no write operation), SysR-P-F-10 (by extension — ingestion is structurally the platform's exclusive corpus-write path). *Verification:* I (interface inspection — no write-capable operation or bypass parameter exists in SRS-RET-IF-01/SRS-RET-IF-02), T. No Phase A eval case exercises an attempted client-side corpus write specifically; this is consistent with the fact that no such path is specified to exist, so there is nothing for a negative case to attempt — noted for completeness, not as a gap requiring a future eval-set addition.
