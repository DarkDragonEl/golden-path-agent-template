### 0.1 Tailoring declaration

Per the working standard: sections of ISO 29148 §9.5 with no content for a blueprint demo component are marked *Not applicable — tailored out* with a one-line reason, never silently omitted. This document keeps the full seven-section skeleton of `srs/SRS-APR.md` and `srs/SRS-AGT.md` — like `srs/SRS-RET.md` and unlike `srs/SRS-MIT.md`'s interface-only depth, which structurally omits §§1/3/5–7 by mission directive. That structural omission does not apply here: this document's assigned depth is **Medium** (`MISSION_PHASE_B0.md`'s deliverable table: "Eval harness + local CLI \| Medium \| SysR-P-F-03/07, SysR-A-EVL-01"), not interface-only. Medium depth is expressed as: every section present and real, but populated more lightly than the Full-depth siblings. §4 (Security) is tailored out with a one-line reason at that section, using the same mechanism `srs/SRS-APR.md` uses for its own Performance tailoring — a documented, reasoned omission, not a structural one; §5 (Quality) tailors Performance and Usability out for the same reason but keeps a deterministic-scoring quality requirement in, since it is directly forced by this component's own nature rather than by another component's ownership. Verification methods: I (inspection), A (analysis), D (demonstration), T (test) — same conventions as the SyRS and its sibling SRS documents. Where two methods are listed, the first is primary.

### 0.2 Purpose and scope of the software item

The evaluation harness and its local command-line interface execute the version-controlled evaluation set (Phase A, `eval/`) — identically on a developer workstation (SysR-P-F-02, SysR-P-F-03) and in the continuous-integration pipeline (SysR-P-F-05, out of this document's scope) — score each case against its category's structured `expected` outcome, and produce a machine-readable results record that determines the pass/fail gate verdict promotion between environments depends on (SysR-P-F-07). It is the measurement instrument that makes `srs/SRS-AGT.md`'s SRS-AGT-QUAL-01 mechanically enforceable, and the evidence source the promotion gate consumes.

This document resolves two decisions `eval/README.md` and `eval/THRESHOLDS.md` explicitly defer to it, as quoted in full in Associated Documents above: (1) the `eval/cases/domain/` layout mandate, resolved at **SRS-EVH-F-03**, which commits to the existing layout without change; and (2) the `known-gap` tag tooling-enforcement mandate, resolved at **SRS-EVH-F-04**, which states the governance requirement `tools/trace-check` must satisfy.

Out of scope for this item: the eval cases' own content and threshold *values* (already Phase A deliverables in `eval/` — this document specifies the harness that consumes them, not the cases themselves, the same provider/consumer split `srs/SRS-RET.md` applies to corpus content versus the retrieval contract); the pilot agent's behavior being measured (`srs/SRS-AGT.md` — this document is the measurement instrument, not the evaluated subject, the same posture `srs/SRS-RET.md`'s own orphan-check note applies to itself for SysR-A-EVL-01); the CI pipeline's own mechanics and wiring — executing the four SysR-P-F-05 test categories, building the image, generating the SBOM, invoking this harness and consuming its verdict to block promotion — all Phase C, not Phase B0; retrieval and corpus content (`srs/SRS-RET.md`); the mock ITSM tool's own contract (`srs/SRS-MIT.md`); the approval workflow (`srs/SRS-APR.md`); the specific mechanical enforcement of the `known-gap` tag lifecycle and the test-file requirement-reference convention (`tools/trace-check`, built next in this iteration — this document states the requirement that mechanism must satisfy, not the mechanism's own implementation).

## 1. Functional Requirements (SRS-EVH-F-*)

- **SRS-EVH-F-01 — Local evaluation CLI.** The harness shall provide a command-line interface that executes, on the developer workstation: (a) any single named evaluation case, identified by case id — resolved by looking up that id across every file in the authoritative case set of SRS-EVH-F-03, not by assuming a file named `<id>.yaml` exists, since each domain category file is a YAML list of multiple cases — or (b) the complete evaluation suite; and shall produce machine-readable results in the same schema used for CI evaluation results (SRS-EVH-IF-02) in both cases. Not marked PROPOSED — directly forced by SysR-P-F-03's own text.
  *Trace:* SysR-P-F-03. *Verification:* T. Evidence: `eval/cli.py`, confirmed by direct reading, already implements this invocation shape (`action=run`, `--case <id>`, `--all`) and sets `AGENT_MODEL_MODE=fake`/`MCP_MODE=mock` as environment defaults before importing anything that reads agent configuration, per its own module docstring — making a workstation run deterministic and network-free without extra caller configuration, consistent with "on the developer workstation." This requirement formalizes that existing invocation pattern; it does not yet formalize execution *against the domain suite*, which SRS-EVH-F-02 and SRS-EVH-F-03 close. **A further extension this requirement's (a) clause requires, not yet provided by today's implementation:** `eval/cli.py`'s current `--case` resolution is filename-keyed (`CASES_DIR / f"{args.case}.yaml"`), which works only because `EXAMPLE-001.yaml`/`EXAMPLE-002.yaml` each hold exactly one case whose id equals its filename. Under the SRS-EVH-F-03 domain layout, each `eval/cases/domain/<category>.yaml` file is a YAML list of multiple cases (e.g. `knowledge_qa.yaml` holds `KQA-001`..`KQA-015`); no file named `KQA-003.yaml` exists for a filename-keyed lookup to resolve against. Run-one resolution against the domain suite therefore requires an id-field lookup across the loaded case set, not a filename match — the same class of extension SRS-EVH-F-02 flags for `eval/loader.py`/`eval/scorer.py`, recorded here so it is not lost: today's `--case` mechanism resolves 2 of 64 known case ids (the two `EXAMPLE-*` fixtures) and does not yet resolve any of the 62 domain case ids by this route.

- **SRS-EVH-F-02 — Category-aware scoring.** For each of the eight Phase A evaluation categories (`knowledge_qa`, `itsm_read`, `tool_selection`, `draft_request`, `out_of_domain`, `unauthorized_write`, `prompt_injection`, `operational`), the harness shall score a case's recorded agent output against that category's structured `expected` shape (`eval/schema.json`'s per-category `allOf` blocks) using deterministic, mechanically checkable assertions — e.g., tool-name match, policy-state assertion, source-document-id or substring check — and shall not depend on a non-deterministic judge (a second, separate model call) to produce a verdict for any of these eight categories. Not marked PROPOSED: this is forced by extension of SysR-P-F-03 ("executes... the complete evaluation suite... producing machine-readable results") combined with SysR-A-EVL-01 (the nine dimensions those results must be checkable against) — a suite execution that cannot score the domain suite's own structured `expected` shape does not fulfill "the complete evaluation suite" for these eight categories, and it directly closes a gap `eval/README.md` documents explicitly under its own "Phase B must extend the harness" heading: *"Today's `eval/loader.py::EvalCase` model is `{id, description, mode, input, assertions, steps}` — no `category`, `expected`, `tags`, `version`, or `threshold_notes`. To actually execute the cases in `cases/domain/*.yaml` against the agent, Phase B needs to either extend `EvalCase` (or add a parallel loader) to parse this schema, and extend `eval/scorer.py` with category-aware scoring logic that consumes each category's structured `expected` shape."* Direct inspection during this derivation confirms the gap exactly as described: `eval/loader.py::EvalCase` has no `category`/`expected`/`tags`/`version`/`threshold_notes` field, and `eval/scorer.py::score_assertion` has no category-aware branch.
  *Trace:* SysR-P-F-03 (by extension), SysR-A-EVL-01 (harness-side only — the measurement mechanism that makes the nine StR-EVL-01 dimensions mechanically checkable; this trace does not restate "the agent shall meet thresholds," which SRS-AGT-QUAL-01 already owns in full). *Verification:* T (a scored case's verdict is asserted against its category's `expected` shape; repeated-run determinism is separately asserted at SRS-EVH-QUAL-01). No Phase A eval evidence in the conventional sense — this requirement specifies the mechanism that makes the domain cases executable at all; once built, the 62 domain cases themselves become this requirement's test corpus.

- **SRS-EVH-F-03 — Domain case-set layout.** The harness shall read the domain evaluation set from `eval/cases/domain/` (the eight category files named at SRS-EVH-F-02) as the authoritative case source scored against the promotion-gate thresholds of SRS-EVH-F-05. `eval/cases/EXAMPLE-001.yaml` and `eval/cases/EXAMPLE-002.yaml` shall remain a separate harness-mechanics smoke fixture — proving the underlying control-flow plumbing (invoke/resume, the human-approval interrupt, mock MCP mode) runs end to end — and shall never be treated as domain content or scored against a category threshold.

  This document **commits to the existing split without change**, resolving `eval/README.md`'s mandate quoted in Associated Documents above. `eval/README.md`'s own stated reason for the split was verified directly against the implementation during this derivation, not assumed: `eval/loader.py::load_all_cases` is `[load_case(p) for p in sorted(cases_dir.glob("*.yaml"))]` — a non-recursive glob over `eval/cases/*.yaml` that calls `EvalCase(**data)` on every match. Placing `cases/domain/`'s category files (each a YAML **list** of cases) directly in `eval/cases/` would crash that call, breaking `python -m eval.cli run --all` for `EXAMPLE-001`/`EXAMPLE-002` too, since the glob's crash is per-`--all`-invocation, not per-file — confirmed sufficient reason to keep the nested layout. No alternative layout is proposed. Not marked PROPOSED in the sense of an open design choice still awaiting a decision — the decision is made, and made here, as `eval/README.md` required; it is recorded as `DECISIONS.md` DEC-005 for full visibility, since the reasoning (a real implementation-crash constraint, not stylistic preference) is non-obvious enough to be worth a durable record beyond this document's own text. **Same-PR sync rule:** any future change to this directory layout, or to the `eval/cases/domain/` category-file split versus the `EXAMPLE-*.yaml` smoke-fixture split, must land in the same PR as a revision to this requirement — the same obligation `srs/SRS-RET.md`'s SRS-RET-DATA-01 states for `eval/corpus-manifest.yaml`'s field set ("any future change to this nine-field set must land in the same PR as a revision to `eval/corpus-manifest.yaml` and to this requirement"), applied here to the case-set layout rather than a field set. This is the normative sentence `eval/README.md`'s own mandate requires ("A Phase B change that quietly moves or reshapes `cases/domain/` without updating SRS-EVH is a violation of this checkpoint's approval, not a routine refactor") and that this document's Associated Documents section already claims this requirement follows.
  *Trace:* SysR-P-F-03 (the "complete evaluation suite" clause — this requirement specifies which case set constitutes "complete" for this component's domain content), SysR-P-INFO-01 (evaluation-sets clause — the case set's location is part of what "reconstructible from recorded versions" attaches to; see SRS-EVH-DATA-01). *Verification:* I (directory-layout inspection: the harness's case-loading path resolves to `eval/cases/domain/`, and `EXAMPLE-001.yaml`/`EXAMPLE-002.yaml` are excluded from category-threshold scoring). Evidence: `eval/cases/domain/` already contains all eight category files (confirmed present); `eval/loader.py::load_all_cases`'s non-recursive glob (confirmed by direct reading) already structurally excludes them from the pre-existing harness's `--all` run.

- **SRS-EVH-F-04 — `known-gap` tag lifecycle governance.** A case tagged `known-gap` shall be excluded from its category's promotion-gate threshold count (SRS-EVH-F-05) while the implementation gap it names remains open. Once that gap closes — e.g., `agent/nodes/reason.py` gains a model-failure fallback path — any case still carrying the `known-gap` tag shall cause a build failure, not a silent exemption or a warning. This resolves `eval/THRESHOLDS.md`'s mandate, quoted in full in Associated Documents above: *"Enforcement is by tooling, not convention... once the model-failure fallback path lands, any case still carrying the `known-gap` tag is a build failure, not a warning or a logged note. The removal trigger is only real if a missed removal breaks the build."* `eval/THRESHOLDS.md` assigns the *mechanical* enforcement of this rule to "the trace-check/CI step that reads `eval/cases/`" — this document states the governance **requirement** that mechanism must satisfy; `tools/trace-check` (`MISSION_PHASE_B0.md` Deliverable 2, built next in this iteration) is where the detection mechanism is actually implemented, a forward reference in the same posture `srs/SRS-AGT.md` used for `srs/SRS-RET.md` before it existed. `Resolved at Checkpoint B0-b — declarative signal, not static code inspection:` the mechanical signal `tools/trace-check` uses is the presence or absence of the `known-gap` tag on the affected `operational.yaml` case(s) (currently OPS-004), read from the version-controlled thresholds file (`eval/THRESHOLDS.md`/`eval/thresholds.yaml`) — not static inspection of `agent/nodes/reason.py`, or any other source file, for a try/except or equivalent guard. Rationale: coupling the check to implementation structure is fragile in both directions — a legitimate refactor of the guard's shape would fail the check falsely, and an unrelated try/except elsewhere in the function would satisfy it falsely. The tag-based signal is self-verifying rather than trust-based: removing the tag admits the case into its category's gate in the same run, so a dishonestly-removed tag immediately fails the gate unless the fallback path actually works — the tag's own removal is the assertion under test, not a separate claim `tools/trace-check` has to independently corroborate against source structure. This also matches the already-adopted Phase B mechanics: the fallback path and the tag removal land in the same PR, per `eval/THRESHOLDS.md`'s own mandate quoted above. Confirmed by direct reading during this derivation, as motivating context for why the gap this signal exists to detect is real and not hypothetical: `agent/nodes/reason.py`'s model call (`model.complete(...)` inside `reason_node`) has no `try`/`except` around it today — `grep` for `try`/`except` across `agent/nodes/reason.py` returns nothing, while `agent/nodes/tool_invoke.py` and `agent/nodes/retrieve.py` each do have one — confirming `eval/THRESHOLDS.md`'s "unguarded" claim precisely, and confirming the gap this requirement's trigger condition names is real and currently open.
  *Trace:* SysR-P-F-07 (by extension — a gate that continues silently exempting a case whose named gap has closed no longer "meets the version-controlled thresholds," it evades them undetected). *Verification:* T (deferred to `tools/trace-check`'s own test suite, forward reference: a synthetic test tags a case `known-gap`, simulates the gap closing via whatever sentinel is chosen, and confirms the check fails the build). No Phase A eval evidence — this is a governance property over the case set's own metadata, not an agent-behavioral property a case's `expected` block can assert.

- **SRS-EVH-F-05 — Promotion-gate evaluation.** The harness shall compare a run's per-category results against the version-controlled per-category thresholds defined in `eval/THRESHOLDS.md`, expressed as **maximum absolute failures allowed** per category — not a percentage, per Checkpoint 1's approved condition on that file (`eval/THRESHOLDS.md`: *"Expressed as maximum absolute failures allowed, not percentages: at n=5–15 cases per category, a percentage misleads"*) — and shall produce an overall gate verdict of pass or fail. A run in which any category exceeds its threshold's maximum absolute failures shall produce a fail verdict for the overall run; there is no partial-credit path to an overall pass. SysR-P-F-07's own text scopes thresholds "for the target environment"; this demo/MVP has a single target environment for evaluation-gate purposes — per `CLAUDE.md`'s demo-scope statement ("There is no staging and no production in this scope") — so this requirement specifies exactly one threshold set (`eval/THRESHOLDS.md`, which itself defines only one) rather than per-environment threshold variance. This is a deliberate scoping choice, stated here rather than left silent: if a later phase introduces multiple target environments, per-environment threshold variance is a forward extension of `eval/THRESHOLDS.md` and of this requirement, not a gap this document is silently ignoring. This document's scope ends at the verdict: Phase C's CI pipeline (out of this document's scope) is expected to block promotion on a fail verdict, per SysR-P-F-07's own text ("the system shall block promotion of the agent between environments unless the evaluation suite results meet the version-controlled thresholds defined for the target environment").

  Where a case carries the optional `performance_budget` field (`eval/schema.json`, itself `PROPOSED — pending owner review` at Phase A), the harness's category-aware scoring (SRS-EVH-F-02) shall include a latency/token-budget check against that case's declared `max_latency_ms`/`max_tokens`; per `eval/THRESHOLDS.md`, this check shall remain informative only — never itself a gate criterion — unless and until latency or token consumption is explicitly promoted to a threshold row in `eval/THRESHOLDS.md`, the same as any other threshold. This clause discharges SysR-P-PERF-02's "the evaluation suite shall assess both against the configured per-interaction budgets" clause specifically; the requirement's *recording* clause ("the system shall record, for every interaction, end-to-end latency and token consumption") is already fully owned by `srs/SRS-AGT.md`'s SRS-AGT-PERF-01 and is not restated here — this is a clause-scoped partial trace, mirroring the split-trace pattern `srs/SRS-AGT.md`'s SRS-AGT-DATA-01 already established for SysR-P-INFO-01.
  *Trace:* SysR-P-F-07; SysR-P-PERF-02 (assessment clause only — the recording clause belongs to SRS-AGT-PERF-01). *Verification:* T (negative case: a sub-threshold run's verdict must be fail — the same negative-case verification SysR-P-F-07's own text specifies). No Phase A eval evidence — this is the gate-computation mechanism over results the domain cases produce once SRS-EVH-F-02 exists; it has no evidence of its own until then.

- **SRS-EVH-F-06 — Synthetic-only evaluation content.** Every evaluation case, input value, and expected-outcome value distributed with this blueprint shall be synthetic or public sample data; no case shall contain organization-identifiable content. Not marked PROPOSED: this restates SysR-P-INFO-04's "evaluation examples" clause directly, the same forced posture `srs/SRS-RET.md`'s SRS-RET-F-04 uses for that same SysR's "seeded corpora" clause.

## 2. Interfaces (SRS-EVH-IF-*)

- **SRS-EVH-IF-01 — CLI invocation interface.** The CLI shall expose, at minimum: a run-one operation (a case id argument, executing exactly that case) and a run-all operation (executing every case in the authoritative set of SRS-EVH-F-03); an exit code reflecting the overall gate verdict of SRS-EVH-F-05 (zero for pass, non-zero for fail); and a machine-readable results record (SRS-EVH-IF-02) written to a results file for every invocation. This formalizes `eval/cli.py`'s existing shape, confirmed by direct reading: `argparse` with `action=run`, `--case <id>`, `--all`, and `sys.exit(0 if all(r["passed"] for r in results) else 1)`. A possible future service-level harness invocation (e.g., a CI- or platform-triggered remote run of the same suite) — out of this document's scope, Phase C territory, not yet designed — would sit alongside, not instead of, this local CLI, the same "alongside, not instead of" relationship `srs/SRS-MIT.md`'s SRS-MIT-IF-04 establishes for its REST introspection surface relative to the MCP tool contract; this requirement specifies only the local, developer-workstation invocation.
  *Trace:* SysR-P-F-03. *Verification:* T. Evidence: `eval/cli.py` — argument parsing, environment-default setup, and exit-code behavior all confirmed present by direct reading during this derivation. **Known gap between today's exit code and this requirement's target semantics:** `eval/cli.py`'s current `sys.exit(0 if all(r["passed"] for r in results) else 1)` is all-or-nothing — it requires every case to pass. SRS-EVH-F-05's gate verdict is category-threshold-aware — it tolerates a threshold-defined number of failures per category (e.g., `knowledge_qa` tolerates 1 failure of 15, per `eval/THRESHOLDS.md`). These are different semantics; today's exit code is coarser than "reflecting the overall gate verdict of SRS-EVH-F-05" requires, and will need to change from all-pass to category-threshold-aware once SRS-EVH-F-02/F-05 are implemented, the same not-yet-implemented gap SRS-EVH-F-01's own evidence discussion flags for the domain suite generally.

  This document does not add a separate "requirement-reference" interface item. Eval case `id` fields — category-prefixed, globally unique, per `eval/README.md`'s Tag conventions table — are an established Phase A convention and serve as one of the two anchors `tools/trace-check`'s future check (d) (`# verifies: SRS-<ID>` or an equivalent test-name convention resolving against `SRS-EVH-F-*` IDs) will resolve against once built; the convention itself, and the test-file half of that anchor pair, are `tools/trace-check`'s own scope, not restated here.

- **SRS-EVH-IF-02 — Results record schema.** Each evaluation run shall produce a results record containing at minimum: the evaluation-set version under evaluation; the image digest or build reference under evaluation, together with an explicit type tag naming which kind of reference it is (added at Checkpoint B0-b, see below); a configuration reference; the per-category thresholds applied (SRS-EVH-F-05); per-case pass/fail with detail; per-category aggregate pass/fail counts; and an overall gate verdict.

  **This is a genuine extension, not a formalize-without-revision case** — stated honestly, unlike `srs/SRS-RET.md`'s SRS-RET-DATA-01, which carried `eval/corpus-manifest.yaml`'s nine-field set forward unchanged. Direct inspection of `eval/results/run-20260813T002957.json` during this derivation confirms the current shape is exactly `{timestamp, total, passed, failed, cases[]}` (produced by `eval/reporter.py::write_report`); **none** of evaluation-set version, image digest, configuration reference, thresholds applied, per-category aggregates, or an explicit gate verdict exist in that shape today. This requirement's field list is directly forced by SysR-P-INFO-05's own enumerated text ("evaluation-set version, image digest, configuration reference, thresholds applied, and results") and is not itself PROPOSED; two design choices about *how* to realize that extension are:

  `Resolved at Checkpoint B0-b:` (a) accepted as drafted — the new fields are **additive** to the existing shape — new top-level keys (e.g. `eval_set_version`, `build_reference`, `config_reference`, `thresholds_applied`, `gate_verdict`) added alongside the unchanged `timestamp`/`total`/`passed`/`failed`/`cases[]` — rather than a schema version bump or restructure. Rationale: no existing field is redefined, narrowed, or removed by this extension; `total`/`passed`/`failed` remain correct aggregate counts and `cases[]` remains valid per-case detail under the extended shape, so semantic-versioning discipline (bump only on a breaking change) argues for additive-only. Alternative considered: introduce an explicit `schema_version` field and treat this as a version-2 results schema — not adopted as mandatory here, since nothing about the extension actually breaks a consumer reading only the original five fields, but not ruled out either; an owner may still prefer an explicit `schema_version` marker for future-proofing, which is compatible with, not contradicted by, the additive choice above. (Durable rationale recorded at `DECISIONS.md` DEC-006.) (b) accepted, with a condition — the value of the image-digest/build-reference field when no image has yet been built — the common case for a purely local `eval run` under SRS-EVH-F-01, which happens on a developer workstation and may precede any image build entirely (SysR-P-F-06's image-build step). SysR-P-INFO-05's text presumes an image digest exists, consistent with its role as promotion evidence downstream of a build; this document proposes a build-reference sentinel (the current git commit hash, or an explicit `"local-dev-uncommitted"` marker when the worktree is dirty) as the field's value for pre-image runs, since SysR-P-INFO-05's text does not itself address the pre-build case. Alternative considered: omit the field entirely for local runs — rejected, since a record with a field silently missing is harder to distinguish from a malformed record than one carrying an explicit sentinel value. **Added condition (Checkpoint B0-b):** `build_reference` alone is not self-describing — a downstream consumer (the Phase C MLflow record, promotion evidence) must never be able to mistake a git commit hash for a real image digest. The results record shall carry a companion field, `build_reference_type`, taking exactly one of `image_digest` \| `git_commit` \| `local_dev_uncommitted`, naming which of the three sentinel cases above `build_reference` holds. This is itself an additive field, consistent with (a)'s additive-fields resolution — the full field list is now `eval_set_version`, `build_reference`, `build_reference_type`, `config_reference`, `thresholds_applied`, `gate_verdict`.
  *Trace:* SysR-P-INFO-05 (record-shape/content half — the retention half is SRS-EVH-DATA-03). *Verification:* I (schema inspection), T (field-presence assertion on a produced results record). Evidence: current shape confirmed by direct reading of `eval/results/run-20260813T002957.json` and `eval/reporter.py::write_report`, as stated above.

*Not applicable — tailored out.* The evaluation harness specified by this document is a local, offline tool with no credential or write-path boundary comparable to `srs/SRS-RET.md`, `srs/SRS-AGT.md`, `srs/SRS-APR.md`, or `srs/SRS-MIT.md`, and this reasoning is stated explicitly rather than the section being silently omitted.
