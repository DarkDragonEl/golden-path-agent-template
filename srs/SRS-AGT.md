### 0.1 Tailoring declaration

Per the working standard: sections of ISO 29148 §9.5 with no content for a blueprint demo component are marked *Not applicable — tailored out* with a one-line reason, never silently omitted. Verification methods: I (inspection), A (analysis), D (demonstration), T (test) — same conventions as the SyRS. Where two methods are listed, the first is primary.

Unlike `srs/SRS-APR.md` (which tailors Performance out entirely, since no component-specific latency/throughput target applies to the approval service) and `srs/SRS-MIT.md` (interface-only depth, §§1/3/5–7 tailored out structurally by mission directive), this document tailors out only **Usability**, inside §5: Performance is populated here — SysR-P-PERF-02 and SysR-A-EVL-01's latency/token dimension are directly agent-relevant — the reverse of SRS-APR's tailoring choice, not an oversight.

### 0.2 Purpose and scope of the software item

The pilot agent is the loop-in-pod process that is the first exemplar of the SysR-A architectural and behavioral pattern (SyRS §0.1) — instantiated concretely in this blueprint as the **Platform Knowledge and Request Agent** (per `eval/README.md`), operating in the ITSM scenario adopted at Annex A OI-02. It answers platform, procedure, and known-issue questions grounded in a curated corpus, retrieves read-only enterprise records, and drafts write actions for human approval. A second adopting team's agent, built for a different knowledge domain and a different enterprise tool, must satisfy the same architectural pattern this document specifies for the Platform Knowledge and Request Agent — loop-in-pod hosting, adapter-mediated loop access, client-only runtime dependencies, bounded operation, injection resistance, draft/approve/execute — with its own domain content substituted in; this is the SyRS's own stated intent for the SysR-A-* group (SyRS §0.1: "a second team's agent must satisfy the SysR-A architectural and behavioral pattern for its own domain, but the concrete knowledge domain, tool, and evaluation content are team-specific").

Out of scope for this item: the approval decision's own lifecycle and logic (`SRS-APR`) — the agent is a *client* of the approval service, submitting proposals and reacting to decisions, never implementing decision logic itself; tool execution and tool-side state (`SRS-MIT`) — the agent invokes tool operations, it does not implement them; retrieval-service internals, ranking, and corpus ingestion (`SRS-RET`, not yet derived — see the ordering note above) — the agent is a retrieval *client*, not the retrieval service; evaluation-harness and scoring mechanics (`SRS-EVH`, not yet derived) — the agent is the subject evaluated, not the harness that scores it. This document specifies the agent's client-side requirement at each of these four boundaries: where the other document already exists, by referencing its requirement ID; where it does not yet exist (retrieval only), by stating the requirement directly, as the future authoritative source for that boundary's field-level shape.

## 1. Functional Requirements (SRS-AGT-F-*)

- **SRS-AGT-F-01 — Grounded, cited answers.** The agent shall answer platform, procedure, and known-issue questions using only content retrieved from the approved corpus through the retrieval client contract (SRS-AGT-IF-03); every corpus-derived factual claim in an answer shall carry at least one citation identifying the source document identifier and the document version. `Resolved at Checkpoint B0-b (accepted as drafted):` citation granularity is per corpus-derived factual claim, not merely one citation attached to the whole answer. Rationale: a single answer-level citation cannot distinguish which individual claims in a multi-fact answer are actually grounded, which weakens the groundedness signal eval scoring can mechanically check; SysR-A-F-01's text ("every answer derived from the corpus shall include citations") is satisfied by either reading, so the stronger, more precisely checkable interpretation is adopted. Alternative considered: answer-level-only citation — rejected as a weaker, harder-to-verify groundedness guarantee. **Owner note (Checkpoint B0-b):** Phase A eval cases check answer-level citation presence and source-document identity only; enforcing per-claim citation density is a Phase B scorer concern, not yet implemented — accepting this requirement does not itself close that implementation gap.
  *Trace:* SysR-A-F-01. *Verification:* T (evaluation cases: correctness, retrieval relevance, citation quality). Evidence: `eval/cases/domain/knowledge_qa.yaml` (KQA-001..015) — `citation_required` and `source_doc_ids` are agent-observable, black-box evidence that answers carry citations to the expected documents; they check citation presence and source-document identity, not per-claim citation density, so they are consistent with, not a full substitute for, verifying the PROPOSED per-claim granularity above.

- **SRS-AGT-F-02 — Authorized read-only retrieval scope.** The agent shall invoke retrieval (SRS-AGT-IF-03) in read-only mode only, and shall use as grounding for an answer, or present to the user, only the passages the retrieval interface returns; the agent shall apply no retrieval-authorization logic of its own — authorization is applied by the retrieval interface, on the basis of the initiating user's identity, before any passage reaches the agent.
  *Trace:* SysR-A-F-02, SysR-P-IF-04. *Verification:* T (positive and negative authorization cases). Evidence: `eval/cases/domain/itsm_read.yaml` (ITR-001..008) and `eval/cases/domain/knowledge_qa.yaml` (KQA-001..015) provide agent-observable evidence of the read-only positive path. **Coverage gap, noted honestly:** neither `itsm_read.yaml` nor `knowledge_qa.yaml`, nor any other file in `cases/domain/`, currently exercises the authorization-*negative* dimension of this requirement (a query for a record or document the initiating user is not authorized to view). This is a gap in the Phase A eval set as it stands, not a gap in this requirement's specification; recommended as a future addition to `eval/cases/domain/itsm_read.yaml` and/or a dedicated corpus-authorization case — the same gap-noting convention `srs/SRS-APR.md` uses for its own untested dimensions (e.g., SRS-APR-SEC-02, SRS-APR-SEC-03).

- **SRS-AGT-F-03 — Actionable output.** For an actionable inquiry, the agent shall produce exactly one of: a recommended action, a troubleshooting plan, or a draft request (the payload defined at SRS-AGT-IF-05, submitted per SRS-AGT-F-04). `Resolved at Checkpoint B0-b (accepted as drafted):` exactly one output type is produced per conversational turn. Rationale: SysR-A-F-03's text ("shall produce a recommended action, a troubleshooting plan, or a draft request") does not itself say "exactly one" or forbid combining outputs; the single-output reading is adopted because `eval/cases/domain/tool_selection.yaml`'s design — one `correct_tool` value (`itsm_search_records` \| `itsm_create_request` \| `none`) per case — presupposes single-dispatch as the intended pattern, and each of the three exemplar output types is evaluated as a discrete outcome, never a combination, across the Phase A eval set. Alternative considered: allow multiple outputs in one turn (e.g., a troubleshooting plan *and* a draft request together) — rejected as untested complexity outside the patterns the Phase A eval set exercises.
  *Trace:* SysR-A-F-03. *Verification:* T (evaluation cases per output type). Evidence: `eval/cases/domain/tool_selection.yaml` (TSEL-001..008, one `correct_tool` value per case), `eval/cases/domain/itsm_read.yaml` (recommended-action/lookup path), `eval/cases/domain/draft_request.yaml` (DRQ-001..006, draft-request path) exercise the output types at the agent-observable level.

- **SRS-AGT-F-04 — Draft, approve, execute.** For any action that would create or modify state in an external system, the agent shall submit a structured proposal to the approval service, using the schema at SRS-APR-IF-01 (referenced — see SRS-AGT-IF-05), instead of invoking the write-capable tool operation (SRS-MIT-IF-03) directly. The agent shall invoke the write operation only after the approval service returns a decision of `approved` (SRS-APR-F-02). On a `rejected` or `expired` decision, the agent shall not invoke the write operation, shall inform the user of the outcome, and shall add no separate decision record of its own — the proposal/decision record at SRS-APR-DATA-01 is the sole record of the decision. `Resolved at Checkpoint B0-b — adjudicated jointly with SRS-APR-F-04, agent-as-invoker model (see DECISIONS.md DEC-008):` the agent obtains the decision outcome by querying the approval service for the submitted proposal's current state, correlated by `proposal_id`; the agent — not the approval service — is the component that issues the literal SRS-MIT-IF-03 invocation once `approved` is obtained, executing exactly the `action_arguments` returned by that terminal-state query, never a locally cached copy retained from drafting time. Rationale: SysR-A-F-04's frozen text is explicit that "the agent shall... execute the action," and SRS-MIT-SEC-01 states the write operation is "reachable by the agent"; SRS-APR-F-04's "the service shall release execution... by invoking the tool-contract path" is adjudicated, at this same checkpoint, to describe the service's atomic pending→approved state transition plus making the approved proposal (including its unmodified `action_arguments`) queryable — not a literal tool invocation performed by the service itself. This reading resolves SRS-APR-F-04 and this requirement consistently instead of leaving them in tension, and keeps SRS-APR-F-04 aligned with the frozen SyRS text it derives from. **Added condition (Checkpoint B0-b):** on `approved`, the agent shall execute the `action_arguments` exactly as returned by the approval service's decision/terminal-state query — never a locally cached copy — preserving SRS-APR-F-04's unmodified-arguments guarantee end to end under this agent-as-invoker model; a Phase B integration test shall assert `arguments_executed == arguments_approved`. The FIND-004 query-interface gap this reading depends on is closed by adopting a new, additive `SRS-APR-IF-05 — Terminal-state proposal query` in Phase D (DEC-008); until Phase D delivers the standalone approval service, Phase B realizes this requirement through an explicitly-labeled **interim mechanism** (the agent's own in-process interrupt/resume, plus a `GET /approvals/{session_id}` read endpoint) — labeled as interim wherever the demo script or deploy/demo manual describes it, not only in DEC-008.
  *Trace:* SysR-A-F-04. *Verification:* T (OS-04, OS-05; OBJ-05 zero-unapproved-writes assertion; arguments-equality assertion above). Evidence: `eval/cases/domain/draft_request.yaml` (DRQ-001..006; `approval_requested: true`, `write_executed_before_approval: false`) and `eval/cases/domain/unauthorized_write.yaml` (UAW-001..006) — both agent-observable evidence of the draft-then-gate behavior, consistent with, not a substitute for, a component-level test of SRS-APR-F-02/F-04 in isolation. The decision-outcome query mechanism, the literal-invoker assignment, and the arguments-equality assertion above have no Phase A eval evidence yet; the Phase B integration test is needed once the interim mechanism (this checkpoint's resolution) is implemented.

- **SRS-AGT-F-05 — Safe stop and escalation.** When the agent cannot answer safely, cannot proceed with the current task, or exceeds an operating limit defined under SRS-AGT-F-07, it shall stop deterministically — issuing no further model-driven tool call or proposal submission for that task — inform the user explicitly of the specific condition that caused the stop, and include an escalation reference. This is mode M-06 per SyRS §9. `Resolved at Checkpoint B0-b (accepted as drafted):` the escalation reference is a static, environment-configured contact or channel reference (supplied through SRS-AGT-IF-07's configuration schema), not a live agent-mediated handoff to a human. Rationale: SysR-A-F-05 requires the agent to "provide an escalation path to a human" without specifying the mechanism; a live, agent-initiated handoff (e.g., automatically paging or opening a ticket on the user's behalf) is out of the demo's complexity envelope (CLAUDE.md: one enterprise tool). Alternative considered: an agent-initiated escalation ticket or page through the enterprise tool — rejected as scope creep beyond the one approved tool-operation pair.
  Note: this condition is distinct from SRS-AGT-F-08's out-of-domain refusal. F-05 is the unsafe-condition/limit-exhaustion stop; F-08 is the corpus-boundedness refusal — the two SyRS boundary conditions (SysR-A-F-05 and SysR-A-F-01's implicit refusal complement) are deliberately not conflated here.
  *Trace:* SysR-A-F-05. *Verification:* T (refusal/escalation evaluation cases; OS-07). Evidence: `eval/cases/domain/operational.yaml` (OPS-001..005; `user_informed: true` on every fault path) — agent-observable evidence of the informed-stop behavior. OPS-004 (model-failure fault) is tagged `known-gap` in `eval/THRESHOLDS.md` and excluded from the promotion gate pending Phase B's model-failure fallback path — noted here honestly, not glossed over.

- **SRS-AGT-F-06 — Injection resistance.** Instructions embedded in retrieved corpus content, retrieved tool results, or user input shall not cause the agent to invoke a tool operation, submit a proposal, or take any action outside the policy currently loaded under SRS-AGT-F-09. Enforcement shall be **structural**: every tool invocation and every proposal submission is checked against the loaded policy before being issued, regardless of the apparent source or claimed authority of the instruction that produced it. Each attempt attributable to embedded or injected content that is blocked by this enforcement shall be logged, correlated to the originating session and request identifiers (SRS-AGT-IF-08). `Resolved at Checkpoint B0-b (accepted as drafted):` a "detected attempt" for logging purposes is defined operationally as any policy-check refusal whose triggering request originated from model output influenced by retrieved or user-supplied content — that is, detection *is* the enforcement event, not an independent, separate semantic content-scanning or classifier layer applied to inputs before they reach the model. Rationale: SysR-A-F-06 requires that "each detected attempt shall be logged" but does not specify a detection mechanism distinct from the resistance mechanism; an independent classifier layer is open-ended scope inconsistent with the demo's complexity envelope. Alternative considered: a separate content-scanning/classification layer flagging suspected injection payloads independently of whether an enforcement action was triggered — rejected as scope creep beyond SysR-P-SEC-05's policy-enforcement mechanism.
  *Trace:* SysR-A-F-06, SysR-P-SEC-05. *Verification:* T (OS-10 evaluation cases). Evidence: `eval/cases/domain/prompt_injection.yaml` (INJ-001..008; one exemplar per `injection_source` value — `document`, `tool_result`, `user_message`) — agent-observable evidence (`injected_instruction_ignored`, `unauthorized_tool_calls: []`, `injection_logged: true`) across all three injection-source vectors.

- **SRS-AGT-F-07 — Bounded operation.** The agent shall enforce, per task, configured limits on: per-model-call timeout, per-tool-call timeout, total task timeout, retry count, and the maximum number of reasoning/tool-execution steps. Every limit value shall be supplied exclusively as environment configuration (SRS-AGT-IF-07, per SysR-P-IF-08); no limit value shall be hardcoded in agent source. On exhaustion of any configured limit, the agent shall transition to the safe-stop behavior of SRS-AGT-F-05. `Resolved at Checkpoint B0-b (accepted as drafted):` one "step," for the step-count limit, is defined as one reasoning/tool-execution control-loop cycle, whether or not that cycle includes a tool call. Rationale: a coarser definition counting only tool-invoking passes would leave reasoning-only loops (cycles that consult the model but call no tool) unbounded between tool calls, defeating the purpose of a step limit; SysR-A-F-07's text ("maximum number of reasoning/tool-execution steps") supports counting both kinds of cycle. Alternative considered: count only tool-invoking passes — rejected for leaving reasoning-only loops unbounded.
  *Trace:* SysR-A-F-07, SysR-P-IF-08. *Verification:* T (limit-exhaustion operational tests). Evidence: `eval/cases/domain/operational.yaml` (OPS-001, OPS-002, OPS-003, OPS-005; OPS-003 specifically exercises `max_reasoning_steps_exceeded`) — agent-observable evidence anchored to environment-configured values in the policy bundle, not to values fixed by this document.

- **SRS-AGT-F-08 — Out-of-domain refusal.** When a question is not answerable from the approved corpus reachable through SRS-AGT-IF-03, the agent shall decline to answer rather than fabricate a response drawn from outside the corpus; the decline shall not be accompanied by any tool call. This requirement is the direct logical complement of SRS-AGT-F-01's grounding constraint ("using only retrieval from the approved corpus"): a question with no answer in the corpus has, under F-01, no grounded answer to give, and fabricating one would violate F-01 directly. It is **not** marked PROPOSED for that reason — it is forced by extension of an already-confirmed requirement, the same posture `srs/SRS-APR.md`'s SRS-APR-SEC-01 (fail closed) took without a PROPOSED marker.
  *Trace:* SysR-A-F-01 (by extension), StR-USR-01. *Verification:* T (evaluation cases; refusal/hallucination assertions). Evidence: `eval/cases/domain/out_of_domain.yaml` (OOD-001..006; `refusal: true`, `tool_calls_expected: []`, `hallucination_check: no_fabricated_answer`) and `eval/cases/domain/knowledge_qa.yaml`'s two `must_refuse_if_absent` cases (KQA-003, KQA-015 — refusal to fabricate a figure absent from an otherwise in-domain document) — both agent-observable.

- **SRS-AGT-F-09 — Policy-bundle-governed operation.** The agent shall load its operating policy — permitted tool operations, the operating limits of SRS-AGT-F-07, and the action-classification rules that determine which proposed actions require approval under SRS-AGT-F-04 — from a versioned policy bundle supplied at runtime (SRS-AGT-IF-07); no operating-policy value shall be compiled into the agent image. The agent shall evaluate every tool-invocation and proposal-submission decision against the policy bundle currently loaded. `Resolved at Checkpoint B0-b (accepted as drafted):` the policy bundle is read once at task start and held fixed for that task's duration; it is not hot-reloaded mid-task. Rationale: SysR-P-F-11 requires the policy to be loadable without rebuilding the agent image — a deployment-time/restart-time property — not that it be live-reloaded during an in-flight task; a mid-task hot-reload capability is disproportionate concurrency complexity for the demo tier. Alternative considered: mid-task hot-reload of the policy bundle — rejected for that reason. This mechanism is also what makes SysR-P-OPS-03's independent write kill switch possible: an operator removes the write-capable tool operation from the next deployed policy bundle (a configuration change, per SysR-P-IF-08) while leaving read-capable operations permitted, disabling the agent's write pathway independently of its read/answer pathway without redeploying the image. `tools/trace-check` surfaced this SysR as unclaimed during a full-repository run; on inspection the mechanism was already specified here, just not traced — added as a genuine coverage fix, not a new design decision, hence not marked PROPOSED.
  *Trace:* SysR-P-F-11, SysR-P-POL-01, SysR-P-OPS-03. *Verification:* T (policy update without rebuild, observed across tasks; independently, a policy update removing only write-capable operations is observed to leave read operations functioning). No direct Phase A eval evidence: policy-bundle load/reload mechanics are not black-box observable through the evaluation cases in `cases/domain/`; flagged as a Phase B test need, matching `srs/SRS-APR.md`'s convention for requirements without Phase A evidence (e.g., SRS-APR-F-02, SRS-APR-F-05, SRS-APR-F-06).

- **SRS-AGT-IF-01 — Model client interface.** The agent shall access all language-model capability exclusively through an OpenAI-compatible chat-completions client. The model endpoint and the model identifier(s) available for routing (SRS-AGT-IF-02) shall be supplied entirely by the injected configuration schema (SRS-AGT-IF-07); no endpoint or model identifier shall be hardcoded in agent source.
  *Trace:* SysR-P-IF-01, SysR-A-ARC-01. *Verification:* I (dependency and configuration inspection), T. No dedicated Phase A eval case isolates this requirement — model-client wiring is not black-box observable through `cases/domain/`; a Phase B dependency-inspection check is needed.

- **SRS-AGT-IF-02 — Rules-based model routing with reason codes.** The agent's model-client abstraction shall route every model call over exactly one configured primary route, or over the one configured fallback route when the primary route fails or a configured forced-route rule matches. Every routing decision shall carry a reason code drawn from a closed set (e.g., `primary-selected`, `fallback-on-error`, `forced-route`), included, together with the model endpoint and the model identifier/version actually used for the call, in the per-run telemetry of SRS-AGT-IF-08.
  *Trace:* SysR-P-F-12. *Verification:* T (OS-07: fallback exercised; reason codes asserted in telemetry). Evidence, stated honestly: `eval/cases/domain/operational.yaml`'s model-failure case (OPS-004, expected `fallback_reason_code: "model_failure:endpoint_unreachable"`) is the case authored against this requirement's model-fallback path, but it is tagged `known-gap` in `eval/THRESHOLDS.md` — `agent/nodes/reason.py`'s model call has no fallback path implemented yet — and is excluded from the promotion gate pending Phase B. OPS-001, OPS-002, OPS-003, OPS-005 (tool-side fallback paths) provide agent-observable evidence that the reason-code/fallback *pattern* this requirement generalizes is implemented and working for non-model faults; they are not evidence of the model-routing case specifically.

- **SRS-AGT-IF-03 — Retrieval client contract (authoritative pending SRS-RET).** The agent shall invoke retrieval exclusively through an interface that accepts, at minimum, a query and the initiating user's identity, and that returns passages, each carrying: passage text, source document identifier, document version or effective date, and owner/classification metadata. Authorization shall already be applied to the returned set before any passage reaches the agent (SRS-AGT-F-02). **This document states the field-level shape of the retrieval-client contract first, because SRS-AGT precedes SRS-RET in this iteration's derivation order** (`MISSION_UNATTENDED.md`); `srs/SRS-RET.md`, when it is derived, is required to offer a contract that conforms to this shape, not to narrow or redefine it. This ordering fact is recorded as `DECISIONS.md` DEC-001.
  *Trace:* SysR-P-IF-04, SysR-A-F-01, SysR-A-F-02. *Verification:* T (authorization-filtered retrieval cases). Evidence: `eval/cases/domain/knowledge_qa.yaml` (KQA-001..015, `source_doc_ids`) exercises the passage/source-identifier half of this contract at the agent-observable level; the authorization-filtering half has no Phase A negative-case evidence, per the gap already noted at SRS-AGT-F-02.

- **SRS-AGT-IF-04 — Tool client contract, consumes SRS-MIT.** The agent shall invoke the enterprise tool exclusively through the two MCP tool operations defined at SRS-MIT-IF-02 (`itsm_search_records`, read-only) and SRS-MIT-IF-03 (`itsm_create_request`, write, approval-gated per SRS-AGT-F-04). `Resolved at Checkpoint B0-b (accepted as drafted):` it shall treat SRS-MIT-IF-01's catalog metadata (tool name, semantic version, certification status) as the source of truth for tool identity, rather than assuming a fixed contract independent of that metadata. Rationale: this mirrors, on the consumer side, the provider obligation SysR-P-IF-03 places on the tool contract's own catalog metadata; nothing in SysR-P-IF-02/IF-03 explicitly requires a runtime metadata lookup by the consumer, so this is a design choice strengthening tool-identity robustness, not one forced by the SyRS text. Alternative considered: the agent treats the two tool names/schemas as fixed at build time and never performs a runtime catalog-metadata check — a legitimate, simpler alternative, rejected here only for being less robust to a future tool-contract version change. The agent shall have no invocation path to any tool operation outside this set — consistent with the demo's one-enterprise-tool complexity envelope.
  *Trace:* SysR-P-IF-02. *Verification:* I (schema inspection against SRS-MIT-IF-02/03), T. ## 4. Security Requirements (SRS-AGT-SEC-*)

- **SRS-AGT-SEC-01 — No shared credentials on agent access paths.** The agent shall access the enterprise tool (SRS-AGT-IF-04) and the knowledge corpus (SRS-AGT-IF-03) only under authorization derived from the initiating user's identity together with the agent's own workload identity; the agent shall hold and use no broadly shared credential on either access path.
  *Trace:* SysR-P-SEC-02, SysR-P-IF-05. *Verification:* I (credential inventory), T (access under distinct identities asserted in audit records). No Phase A eval case — credential-provisioning property, not black-box observable; a Phase B identity-inspection test is needed.

- **SRS-AGT-SEC-02 — Read-only-by-default tool scope.** The agent's default operating policy (SRS-AGT-F-09) shall grant no write-capable tool operation; the write-capable operation (SRS-MIT-IF-03) shall be reachable by the agent only via the draft/approve/execute path of SRS-AGT-F-04. This is the agent-side half of SRS-MIT-SEC-01's no-bypass guarantee: SRS-MIT-SEC-01 states that the tool interface itself exposes no bypass path; this requirement states that the agent's own default policy exposes none either.
  *Trace:* SysR-P-SEC-03, SysR-P-POL-01. *Verification:* I (default policy bundle inspection), T (write attempt outside the approval path is denied). Evidence: `eval/cases/domain/unauthorized_write.yaml` (UAW-001..006; `write_blocked: true`, `approval_path_invoked: true` in every scenario, including the explicit bypass-attempt framings UAW-003/UAW-006) — agent-observable, 100% fail-closed per `eval/THRESHOLDS.md`'s gate.

- **SRS-AGT-SEC-03 — Fail closed on ambiguous action classification.** `Resolved at Checkpoint B0-b (accepted as drafted — highest-leverage item in this checkpoint's review, shapes policy/approval_rules.yaml's default_classification: write in Phase B2):` if the agent's loaded policy (SRS-AGT-F-09) cannot determine whether a proposed action requires approval under SRS-AGT-F-04 — because the action type is ambiguous or unrecognized against the policy's classification rules — the agent shall treat the action as write-capable and requiring approval; it shall never treat a classification-ambiguous action as read-only or directly executable. Rationale: SysR-P-SEC-05's deny-path principle and SysR-P-POL-01's read-only-default posture both point toward the conservative default, but neither states the explicit tie-breaking rule for a classification-ambiguous case — this requirement closes that gap at the SRS level, in the same pattern `srs/SRS-APR.md` uses at SRS-APR-SEC-01/SEC-02. Alternative considered: reject the action outright rather than route it to approval — rejected because it would needlessly block a potentially legitimate action a human approver could still approve, whereas silently executing it directly is the actual violation this requirement exists to prevent. **Owner disposition on FIND-003 (Checkpoint B0-b):** closed at the SRS level by this requirement; the SyRS-level clause (an explicit tie-breaking rule at SysR-P-SEC-05/SysR-P-POL-01 themselves) is explicitly deferred to a future SyRS revision, not silently dropped — see `srs/FINDINGS.md` FIND-003.
  *Trace:* SysR-P-SEC-05 (by extension), SysR-P-POL-01. *Verification:* T (a classification-ambiguous action is routed to approval, never executed directly). No Phase A eval case exercises a classification-ambiguous action specifically — `tool_selection.yaml` and `unauthorized_write.yaml` test tool selection and approval-bypass framing, not an unrecognized action type against the policy's own classification rules; recommended as a future addition to `eval/cases/domain/tool_selection.yaml` or `unauthorized_write.yaml`. This gap is recorded as `srs/FINDINGS.md` **FIND-003**, in the same disposition pattern as FIND-001/FIND-002.

- **SRS-AGT-SEC-04 — No embedded secrets.** The agent source repository and the packaged agent image shall contain no secret; the agent shall obtain every secret it needs solely through the injected configuration schema (SRS-AGT-IF-07, SysR-P-IF-08).
  *Trace:* SysR-P-SEC-04. *Verification:* I (image and repository scan), T (CI secret-exposure tests per SysR-P-F-05). No Phase A eval case — repository/image-content property, not black-box observable; CI scan is the intended Phase B/C verification, consistent with SysR-P-F-05's security-test category.
